Это сильная функциональная, но не производственная приёмка [E02, E08, E09].

Три наиболее полезные **практики**, без выдуманного рейтинга агентов:

1. **Spec review на переходах состояния.** Найдены comparison race в P1, source race в Freshness, ошибочное cached origin reentry в NPI-07 и provenance XLSX в NPI-10 [E03–E06].
2. **Проверка через реальное пользовательское действие и HTTP.** После зелёного CI первая приёмка обнаружила два дефекта, затронувших три сценария; финальная проверка установила, какой checkout действительно обслуживает порт [E03, E08].
3. **Независимые численные оракулы и повторное открытие XLSX.** NPI-06 различает знаменатели метрик; NPI-10/11/12 проверяют полноту, типы, literal cells и reconciliation, а не только статус 200 [E05–E08].

Три системные проблемы:

- **Недостаточное раннее покрытие жизненного цикла.** Обычный cache hit, rejected snapshot, editable controls и frozen result проверялись частями; пересечения проявлялись в приёмке и следующих задачах. P1 и Freshness — разные подтверждённые пробелы, а не одно неудачное исправление [E03, E04].
- **Отсутствие обязательной проверки запущенной ревизии.** Изолированные worktrees защищали работу, но пользовательский сервер остался на старом checkout. Совпадение HTML/JS доказано хешами [E08].
- **Повторная верификация и тяжёлый архив.** Три review на каждую задачу предписаны локальными требованиями; часть заключений повторяет уже известные ограничения. 315 tracked evidence-файлов занимают 71,036,036 байт. PR #19 содержит +209,164 строк, хотя production code не меняет. Избыточность части работы — INFERRED; полная стоимость UNKNOWN [E01, E02, E09].

Сохранить: обязательный полный CI на итоговом кандидате и main, защиту от skipped frontend tests, проверку сохранённой идентичности/полноты/безопасности данных, воспроизводимый RED дефекта, отдельное функциональное и человеческое принятие. Изменить: review выбирать по риску; выполнять live smoke при первом затронутом переходе; в каждый запуск включать проверку ревизии/порта; evidence хранить один раз. Объединить: Standards/Spec/Ponytail замечания и dispositions в одну таблицу PR, сохранив автора и независимость. Убрать из обязательного маршрута: третий универсальный review для простых docs/presentation задач и повторную локальную полную проверку после правки только текста отчёта. Это предложение, не уже внедрённое правило [review-effectiveness](review-effectiveness.md).

Workflow v2: один ответственный исполнитель → public-contract тест и затронутые соседи → reviewer по риску → полный CI на final SHA → объединённый main → запуск проверенной ревизии → функциональная приёмка → отдельное human acceptance. Для сложных данных/архитектуры независимые Spec и Standards, Ponytail как дополнительный проход по конкретным рискам. Новые роли не нужны [workflow-v2](workflow-v2.md).

Первые пять действий:

1. Включить проверку checkout/interpreter/port/served assets в инструкции запуска и приёмку.
2. Завести одну компактную матрицу transitions: cache/revision/conflict/restart/cancel/frozen controls/export.
3. Принять риск-ориентированную схему ревью; итоговый CI оставить полным.
4. Сократить публикацию evidence до уникальных RED/GREEN, наблюдений, ключевых screenshots и manifest.
5. Получить реальный объём regional All и latency target; отдельно получить человеческую приёмку XLSX/UI.

Экономия не измерена. Проверяемый пилот: на следующих пяти задачах сравнить review turns, повторные полные прогоны, минуты CI, evidence bytes и escaped defects. Удаление одного из трёх review уменьшает количество review dispatches на 33% для подходящей задачи, но не доказывает 33% экономии времени/токенов. Численные денежные обещания не обоснованы.
